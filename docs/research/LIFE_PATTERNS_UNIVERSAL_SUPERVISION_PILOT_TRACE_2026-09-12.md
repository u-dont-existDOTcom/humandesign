No durable project evidence was found proving that the relevant universal controls were compiled into the Life Patterns reasoning task at the consequential fork.

This establishes a routing/activation deficiency. It does **not** prove which instructions may have happened to be present in a particular historical model context.

### 2. Semantic control gap: manufactured prerequisite

The owner-facing outcome could remain intact while an assistant-created method became a mandatory dependency:

`same frozen theory-blind substrate for every target model`

was silently hardened into:

`therefore a comprehensive externally coded behavioral ontology/coder is required`.

Ordinary owner-outcome alignment can miss this because the final requested product is still promised. Outcome-progress controls can catch the strategy later when evidence becomes flat/regressive, but they are not the earliest gate at the moment of method commitment.

The prior-work scan also lacked an explicit necessity test. Once the problem was framed as ontology construction, high-quality literature about ontology engineering, psychometrics, codebooks, annotation, and inter-rater reliability could improve the chosen paradigm without establishing that the paradigm itself was required.

### Candidate repair A — method necessity

`templates/PRIOR-WORK-SCAN.md` gains a `Method necessity / manufactured-prerequisite check` only for consequential method commitments.

It separates:

- owner outcome;
- genuine constraint + source;
- proposed method + origin;
- what fails if the method is removed/replaced;
- strongest materially simpler alternative;
- evidence that rules the alternative out;
- ordinary-case specimen + difficult counterexample;
- necessity state: `ESTABLISHED | UNRESOLVED | NOT_NECESSARY`.

An `UNRESOLVED` assistant-inferred method may be tested reversibly but should not be hardened into architecture first.

### Candidate repair B — activation provenance

The existing task-time lesson pattern and Active Lesson Contract are extended so a task must identify **how current guidance actually entered the reasoning path** before claiming that universal/project controls protected it.

Valid activation routes include:

- current project `AGENTS.md` / bootstrap;
- current task or owner directive;
- authenticated supervision/admission supplying current guidance.

`rule exists in GitHub` and `the model may know it` are explicitly not activation evidence.

This does **not** force every repository to adopt UDA. If the project has not adopted it and no current directive activates it, status is simply `NOT_ACTIVATED` and project-local authority governs. If current authority says UDA does govern the task, `NOT_ACTIVATED` or `STALE` blocks the affected consequential method commitment/delivery until current guidance is actually loaded.

### Owner-facing supervision surface

`templates/METHOD-FORK-CARD.md` gives a compact view only at a material fork:

1. what the owner asked for;
2. what the assistant is additionally assuming;
3. why the assumption matters;
4. simplest live alternative;
5. what would fail without the added method + evidence;
6. one concrete ordinary case;
7. current method status;
8. recommended next action;
9. `Owner action: NONE | DECISION_REQUIRED`.

A cheap reversible discriminating probe should normally produce `Owner action: NONE`; the system should not turn better supervision into routine approval requests.

## Development fixtures

The pilot includes both positive catches and controls where complexity is correct.

Method-necessity development cases:

1. Life Patterns known incident -> `UNRESOLVED`, bounded experiment only.
2. Owner explicitly requests standardized taxonomy/inter-rater coder -> `ESTABLISHED`.
3. Routine reversible internal refactor -> gate not triggered.
4. Verified hard external schema requirement -> `ESTABLISHED`.

Activation cases distinguish:

- rules merely existing but unwired -> `NOT_ACTIVATED`;
- explicit project bootstrap + current contract -> `ACTIVE`;
- current direct task/owner activation without permanent bootstrap -> `ACTIVE`;
- required guidance bound to stale contract -> `STALE`.

These expected results are development labels, not an independent model benchmark.
